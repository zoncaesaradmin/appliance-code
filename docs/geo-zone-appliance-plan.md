# Geo-Zone appliance integration

This change establishes the appliance contract for the Geo-Zone product from
`zone-studio` without importing its standalone installer or its private
SuperTokens deployment. Geo-Zone is represented by one delivery pack and
granular capabilities:

- `geo-spatial-store` — PostGIS-backed boundary persistence and migrations.
- `geo-data-api` — authenticated spatial queries and GeoJSON export.
- `geo-basemap` — map style, tiles and attribution. The current port preserves
  the connected OpenFreeMap style used by Zone Studio; an appliance-owned
  offline archive remains the production hardening path.
- `geo-zone-editor` — the MapLibre/Terra Draw editor and its static assets.

The `geo-zone` profile selects all four capabilities plus the shared `base` and
`application-auth` capabilities. `geo-stack` is the sole delivery pack for the
Geo-Zone-specific artifacts; it is intentionally not split into one pack per
service.

The Geo employee entrypoint and Zone Studio editor are now delivered as a
second static entrypoint in the shared appliance UI image. `/geo/login` uses
the appliance's local username/password session API and `/geo` serves the
MapLibre/Terra Draw editor. Geo data requests remain behind the control-plane
`/api/v1/geo/*` proxy and are authorized with `geo.read` and `geo.write`.

The Geo runtime workloads run in the Kubernetes namespace `ace-app-geo`, and
the service endpoint is `geo-data-api.ace-app-geo.svc.cluster.local`. Existing
installations that still use the former `geo` namespace require an explicit,
data-preserving migration before upgrading; changing this value alone must not
be used as an in-place storage migration.

Runtime images, the PostGIS chart/migrations and the data API must still be
added as signed release-input artifacts before the Geo profile is offered for a
production install. The editor now renders the geographic OpenFreeMap style by
default, matching the standalone POC; `VITE_MAP_STYLE` can replace it with a
local signed style, and `VITE_MAP_STYLE=offline` remains available for local
development. Its persistence API is intentionally fail-closed when the Geo
data service is absent.

## User flow

1. Install or activate the `geo-zone` profile with the signed `geo-stack`
   pack present.
2. Complete normal appliance setup and create the first local administrator.
3. Open `/geo/login` and sign in with that local username/password. A
   successful session lands at `/geo`; `/console/login` remains the separate
   appliance-operations entrypoint and `/app/login` remains the OTP-based
   application entrypoint.
4. The built-in administrator already has `geo.read` and `geo.write`. For
   other employees, assign those permissions through a local role before
   granting them Geo access.

The UI and login boundary are therefore usable before the persistence service
is shipped, while missing Geo runtime artifacts cannot silently become an
internet-backed or unauthenticated fallback.

## Zone listing and S3 snapshot export

`GET /api/v1/geo/zones` returns the complete live list from Postgres. Every
zone has a stable UUID (`id`) generated by the database; the Geo workspace
shows that ID beside the name and searches by either name or ID.

`GET /api/v1/geo/snapshots` lists the snapshot manifests currently present in
the configured target. `POST /api/v1/geo/snapshots/export` creates a new one;
both control-plane routes require Geo authentication, and creation requires
`geo.write`. The Geo workspace has a Snapshots panel with Refresh and Create
snapshot actions, while the server keeps all S3 credentials out of the
browser. When the `geo.snapshot` target is configured, the Geo API reads one
consistent Postgres export and publishes three S3-compatible objects in this
order:

1. `<prefix>/<snapshot-id>.geojson.gz` — gzip-compressed GeoJSON
   `FeatureCollection`, including each zone's UUID and properties.
2. `<prefix>/<snapshot-id>.manifest.json` — schema version, zone count, byte
   counts, object key, and SHA-256 of the uncompressed GeoJSON.
3. `<prefix>/current.json` — a pointer containing the same manifest fields.

The receiver reads `current.json`, downloads the manifest and content, checks
the SHA-256 and `zoneCount`, decompresses GeoJSON, validates the
`FeatureCollection`, and replaces its target in one transaction. Immutable
snapshot objects are written before `current.json`, so a failed upload leaves
the previous pointer intact. The format is a single read-all snapshot and is
appropriate for the current POC scale of roughly 2,000 polygons.

The UI and APIs are always part of the Geo service. The S3 target is an
explicit operator configuration, so S3 does not become a hidden install
dependency. Provide an operator-managed Secret in the Geo namespace with
`accessKey` and `secretKey` keys, then set `geo.snapshot.endpoint`, `bucket`,
`credentialsSecretName`, and (optionally) `prefix` in the signed install
values. Until that is configured, the UI shows a clear “storage is not
configured” state rather than pretending that a snapshot was created. The
receiving application should use a read-only credential scoped to that prefix.

The non-secret Helm values are intentionally ordinary configuration:

```yaml
geo:
  snapshot:
    enabled: true
    endpoint: https://s3.example.internal
    bucket: zonity-snapshots
    region: us-east-1
    prefix: geo/zones
    credentialsSecretName: geo-snapshot-credentials
```

`geo-snapshot-credentials` is created separately in `ace-app-geo` with
`accessKey` and `secretKey`; it is mounted as protected files in the Geo API
pod and never returned by the API or rendered into the UI.

The reusable reader/import code lives in
`sdk/golang/geosnapshot`. An application-core consumer adapts its S3 client to
the package's `ObjectStore`, calls `geosnapshot.Read(ctx, store, prefix)`, and
then calls `geosnapshot.Load(ctx, geosnapshot.PostgresLoader{DB: db}, snapshot)`.
The loader invokes the canonical `api.import_zones(jsonb)` function from the
Geo schema, which validates geometry, preserves stable UUIDs, and replaces the
target set atomically. This keeps the producer and future application-core
consumer on one snapshot format and one decompression/verification path.

The standalone Zone Studio catalog remains useful as the source inventory, but
its `ingress`, `auth-service`, and `backups` components map to appliance-owned
concerns: Traefik, the common foundation Auth Service, and the appliance
recovery-set/backup contract. They are not duplicated as Geo-specific packs.
